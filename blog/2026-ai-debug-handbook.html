AI 写的代码跑不起来怎么办：普通人的排查手册When AI-Generated Code Won't Run: A Debugging Handbook for Non-Developers

2026.10.22 — 从"它又坏了"到 20 分钟定位问题，一套能照着做的流程2026.10.22 — From "it's broken again" to a 20-minute diagnosis, a process you can actually follow

先说一个反直觉的结论An Uncomfortable Conclusion First

我统计过自己 2026 年上半年用 AI 写代码的记录：所有"跑不起来"的时刻里，真正需要理解代码才能解决的占 18%，剩下 82% 都是"信息没给够"或者"指令没说清"——也就是说，大部分时候你不需要会写代码，只需要知道怎么把情况描述清楚。 I went back through my own AI coding sessions from the first half of 2026. Of every "it won't run" moment, only 18% actually required understanding the code. The other 82% were "I didn't give it enough information" or "my instruction was ambiguous" — which means you mostly don't need to write code, you need to know how to describe the situation precisely.

但普通人的真实体验是：报错信息像天书，问 AI 它又改出新问题，改了三轮更糟了。这个循环我见过太多次——包括我自己。所以这篇不讲"怎么成为程序员"，只讲一件事：怎么在 20 分钟内把一个报错的 AI 代码，变成一个能跑的。 But the typical experience is: the error message looks like gibberish, you ask AI, it introduces a new problem, and after three rounds it's worse than before. I've seen that loop too many times — including running it myself. So this isn't about becoming a programmer. It's about one thing: getting a broken AI-written feature running within 20 minutes.

本文的核心方法只有一句：不要描述"它坏了"，要描述"我做了什么、期望什么、实际发生了什么"。前者是抱怨，后者是任务描述——AI 只会认真对待后者。The method behind this article is one sentence: don't describe "it's broken" — describe "what I did, what I expected, what actually happened." The first is a complaint; the second is a task description. AI only takes the second seriously.

为什么逻辑错最值得警惕Why Logic Errors Deserve the Most Caution

Logic errors are silent: the UI renders, the flow completes, the numbers are just wrong. The most expensive one I've seen was a reconciliation routine that was correct on test data and missed a transaction on real data because of one dirty record. The customer found it two months later.

第三步：把情况描述清楚Step 3: Describe the Situation Clearly

这是整篇文章最重要的一节。AI 看不到你的屏幕，也看不到你的文件——它只能看到你打的字。你给的信息越少，它只能猜；它猜错之后还得改，于是你越问越乱。 This is the most important section of the article. AI can't see your screen or your files — only what you type. The less you give it, the more it guesses; and when it guesses wrong it has to change something, which is how the loop spirals.

会越问越乱的问法The request that spirals

"这个功能又坏了，你帮我看看。"

AI 只能反问你，或者凭猜测改代码。改完你再测，还是坏，再问，它再改。三轮之后你手里有 4 个版本的代码，没有一个能跑，而且你也说不清现在是哪个版本在跑。

根因：它不知道你的运行环境、不知道你期望什么、不知道你已经试过什么。 "This feature is broken again, take a look."

AI can only ask you questions or guess at edits. You test, it's still broken, you ask again, it edits again. Three rounds later you have four versions of the code, none of which runs, and you can no longer say which one you're running.

Root cause: it doesn't know your environment, your expectation, or what you've already tried.

一次就能收敛的问法The request that converges

"运行 npm run dev 后访问 /invoice 页面，浏览器控制台报 TypeError: Cannot read properties of undefined (reading 'total')，位置在 src/features/invoice/summary.tsx 第 42 行。我期望显示发票总额 1280 元，页面显示空白。后端 /api/invoice/123 返回正常。请先只做一件事：告诉我第 42 行那个值为什么是 undefined，不要修改任何文件。"

根因：四要素齐全——环境、期望、实际、边界。 "After npm run dev, opening /invoice gives TypeError: Cannot read properties of undefined (reading 'total') in the console, at src/features/invoice/summary.tsx line 42. I expect a total of 1280; the page is blank. The backend /api/invoice/123 responds fine. Do one thing only: tell me why the value at line 42 is undefined. Don't change any files."

Root cause: all four elements present — environment, expectation, actual, constraint.

五个区块各干一件事：环境让 AI 不用猜版本，动作让它知道你在哪一步，期望 vs 实际把"坏了"变成可描述的差异，报错原文避免二次转述失真，已排除项防止它在同一个地方绕圈。最后那句"先只做分析，不要改文件"，把"诊断"和"修复"分成两轮——这一句能把改坏代码的概率降低一半以上。Each block does one job: environment stops it guessing versions; action says where you are; expected vs actual turns "broken" into a describable gap; raw error avoids distortion through retyping; already ruled out stops it circling the same spot. 一次真实的排障记录A Real Debugging Session

第 1 天：我怀疑环境（猜错了）Day 1: I Suspected the Environment (Wrongly)

第 2 天：我用对了模板（找到方向）Day 2: I Used the Template Properly (Found the Direction)

这次我按五要素写：环境、动作、期望、实际、报错原文。AI 看完第一句话就说："你报的是前端报错，但这个错误在服务端日志里。给我服务端日志。"我贴了服务端日志，里面写着 Cannot find module './config'——服务器上少了一个配置文件。改完就好了。This time I used all five elements. AI's first sentence was: "You're showing me a frontend error, but this error lives in the server log. Give me the server log."I pasted it: Cannot find module './config' — a config file was missing on the server. Fixed, done.

第 3 天：我把流程固化了Day 3: I Made It a Process

我在项目里放了一个 BUG_REPORT.md 模板，以后每次报错先填这个模板再问 AI。同时写了一条部署检查清单：配置文件、环境变量、目录结构。从那以后，同类问题平均 12 分钟解决。I added a BUG_REPORT.md template to the project and fill it in before asking AI anything. I also wrote a deployment checklist: config files, env vars, directory structure. Since then, the same class of problem averages 12 minutes.

三天里我真正学到的不是"怎么修这个 bug"，而是"我第一天缺了什么信息"。第一天我以为 AI 应该猜得到服务器上缺文件——它猜不到，因为它看不到我的服务器。 What I learned in those three days wasn't "how to fix this bug" — it was "what information did I withhold on day one." I expected AI to guess that a file was missing on my server. It couldn't; it can't see my server.
顺手做的一件事The One Thing Worth Copying

在项目根目录放一个 BUG_REPORT.md，里面写好五个小标题：环境、我在做什么、期望、实际、报错原文。每次报错你只需要往里填，不用重新组织语言。这个文件我到现在每个项目都有。Put a BUG_REPORT.md in the project root with five subheadings: Environment, What I'm doing, Expected, Actual, Raw error. Each failure just means filling it in, not re-organizing your words.I still have this file in every project.

让 AI 自己验证的三招Three Ways to Make AI Verify Its Own Work

最好的修 bug 方式，是让 AI 修完之后自己证明它修好了。下面三招按有效性排序。 The best way to fix a bug is to make AI prove it fixed it. Here are three techniques, best first.

第一招：让它自己跑1. Make It Run the Code

如果你的项目有测试（哪怕只有一个），直接说"改完运行 npm test，把失败的用例贴给我"。这招最有效，因为它把"我改好了"变成"测试证明了它改好了"。这是我推荐所有人做的第一件事——哪怕只写一个测试。 If your project has any tests at all, say "after changing it, run npm test and paste the failures." This is the most effective technique, because it turns "I fixed it" into "the test proves it." This is the first thing I'd tell anyone to set up — even a single test.

第二招：让它自己复现2. Make It Reproduce

"先写一个能稳定复现这个 bug 的脚本或测试用例，让它跑出失败，然后再修。"这一招的价值在于：如果它写不出复现脚本，说明它自己也没搞清楚问题是什么——这时候就该停下来重新描述，而不是让它继续改。 "First write a script or test that reliably reproduces this bug, run it and show it failing, then fix it." The value: if it can't write a reproduction, it doesn't understand the problem either — and that's your signal to stop and describe the situation again, not to keep editing.

第三招：让它列出所有改动3. Make It List Every Change

"改完之后给我一个清单：改了哪些文件、每个文件改了什么、为什么。"这一招防的是"顺手优化"——AI 经常在修 bug 的同时改掉别的东西，而你不看 diff 就发现不了。改完先看清单，再看 diff，最后再合并。 "After you're done, give me a list: which files changed, what changed in each, and why." This guards against drive-by "improvements" — AI often edits unrelated things while fixing, and you won't notice without looking at the diff. Read the list, then the diff, then merge. 

修复完成后，请依次做这三件事，每件做完停下等我确认：

1. 运行 npm test，把结果原样贴给我（包括通过数量）
2. 给我一个改动清单：文件名 / 改了什么 / 为什么改
3. 指出这次修改可能引入的 2 个新问题，以及怎么验证它们

不要改动本次修复无关的文件。
如果测试仍然失败，直接告诉我失败，不要继续尝试新的修改。
一个反直觉的结论A Counterintuitive Conclusion

"让 AI 自己跑"这一招，会让它修得更慢，但错得更少。我统计过：要求"改完自己跑测试"之后，同一类 bug 的平均修复轮次从 2.4 轮降到 1.6 轮。慢了一点，但一轮就对的概率高得多。"Make AI run it" makes it slower but less wrong. In my logs, adding "run the tests after you change it" dropped average fix rounds for the same bug class from 2.4 to 1.6. A little slower, far more often right on the first go.

什么时候该放弃重写When to Stop Rewriting and Start Over

有一种失败模式比修不好更糟：你和 AI 反复重写同一个功能，永远差一点。这种情况下继续修是浪费。判断标准有三个，命中任意一个就该停下来。 There's a failure mode worse than not fixing it: you and AI rewrite the same feature forever, always a little short.At that point, continuing is waste. Three signals mean stop.

  • 改到第 5 轮还在原地打转：第 5 轮的报错和第 3 轮几乎一样，说明你们的理解始终没对齐，问题不在代码，在描述。继续改只会越改越乱。Round 5 looks like round 3 — if the error barely changed, your two descriptions never aligned. The problem isn't the code, it's the description. More edits only make it messier.
  • AI 开始"顺手优化"不相关的地方：这是它在用改代码代替思考。正确做法是回滚这一步，把问题拆成更小的一块再问。AI starts "improving" unrelated code — it's editing instead of thinking. Roll that step back, split the problem smaller, and ask again.
  • 你说不清"它到底应该做什么"：最常见也最致命。如果你只能用"就是不对"来描述，那 AI 收到的就是"就是不对"，它只能瞎猜。这时候该回去写需求，不是回去修代码。You can't say what it should do — the most common and the most fatal. If all you have is "it's just wrong," that's all AI gets. Go back to requirements, not to code.
最坏的一种循环The Worst Loop of All

你描述不清楚 → AI 猜 → 改坏 → 你更混乱 → 描述更不清楚。打破点永远是回到起点：把"我想要什么"用一句人话写出来，而不是继续往对话里塞报错。实在写不出来，就先别用 AI，自己用笔写五分钟。You describe badly → AI guesses → breaks more → you're more confused → you describe worse. The way out is always to go back to the start: write what you want in one plain sentence instead of feeding more stack traces into the chat. If you truly can't, stop using AI for five minutes and write it by hand first.

一份排查清单A Debugging Checklist

保留现场Preserve the Scene

报错时别急着关终端。先截图或复制完整输出，包括前后各 20 行。很多时候重跑一遍就看不到那段了。Don't close the terminal. Screenshot or copy the full output including 20 lines either side. Sometimes it's gone on the next run.

先分类，再动手Classify Before You Touch Anything

语法错、运行时错、逻辑错，三条路完全不同。先用 30 秒判断属于哪一类，能省掉一小时。Syntax, runtime, or logic — three different roads. Thirty seconds of classification saves an hour.

先排除，再提问Rule Out First, Then Ask

把"我已经确认没问题的部分"列出来（后端通吗？依赖装了吗？环境变量配了吗？），再问 AI。带着排除清单提问，答案质量差别很大。List what you've already ruled out (backend up? dependencies installed? env vars set?), then ask. The difference in answer quality is large.

一次改一处One Change at a Time

每改一处就测一次。AI 一次给五个建议时，坚持让它按顺序来，你确认一个它做一个。Test after each change. When AI offers five suggestions at once, insist it go in order, one at a time, with your confirmation between.

看 diff 再合并Read the Diff Before You Merge

最后一步，也是最容易被跳过的一步。AI 改完不读 diff 就合并，等于没看过自己项目的代码。养成习惯：这行 diff 你读不懂，就别合。The last step, and the most-skipped. Merging without reading the diff means you never saw your own code.Make it a rule: if you can't read the line, don't merge it.

最后一句：会修 bug 不是 AI 编程的核心技能，"会描述问题"才是。前者需要读代码，后者只需要你真的知道自己要什么——而后者恰恰是 AI 帮不了你的部分。所以每次报错，别急着贴终端，先花一分钟想清楚"我到底要它做什么"。Closing thought: the core skill isn't fixing bugs, it's describing them.Fixing needs you to read code; describing needs only clarity about what you want — and that's precisely the part AI can't do for you. So before you paste the terminal output, spend a minute deciding what you actually want it to do.

写在最后Closing Thoughts

那份白屏了三天的报销单工具，最后只改了一行：一个文件名的大小写。而找到它花了我两天，因为第一天我一直在让 AI 改代码，而不是在告诉它我的服务器上少了什么。 The expense-sheet converter that stayed blank for three days turned out to be one character: a filename's case. Finding it took two days, because on day one I kept asking AI to change code instead of telling it what my server was missing.

如果你正在跟一个跑不起来的 AI 代码较劲，先停一下，问自己一句：我是不是还没告诉它"我做了什么、期望什么、实际发生了什么"？大概率答案是"还没"。那这三行字就是你现在最该做的事。 If you're currently fighting code that won't run, stop and ask yourself: have I actually told it "what I did, what I expected, what happened"?The answer is almost certainly "no." Those three lines are what you should do right now.
