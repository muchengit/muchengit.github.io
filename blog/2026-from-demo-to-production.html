从 Demo 到上线：AI 生成代码的生产化改造清单From Demo to Production: A Production-Readiness Checklist for AI-Generated Code

2026.09.15 — 五周改造，从「能跑」到「能上线」的完整清单2026.09.15 — Five weeks of turning a working demo into a product that survives real users

「它跑起来了」是我最常说的一句话"It Runs" Was My Most Repeated Sentence

2026 年 5 月，我用 AI 做了一个小工具：上传一份合同，AI 帮你标出可能踩坑的条款——付款周期太长、违约金对不上、无限责任、没写验收标准这种。代码全部由 AI 生成，从前端界面到后端接口，5 天搞定。本地 localhost 打开一切正常，界面还挺像样。 In May 2026 I used AI to build a small tool: upload a contract and the AI flags the clauses that are likely to bite you — payment terms that are too long, mismatched penalties, unlimited liability, missing acceptance criteria. Every line was AI-generated, from the frontend to the API, and it took five days. It ran perfectly on localhost, and the interface looked decent.

我给三个朋友演示，每个人都说"这就能直接卖了吧"。我信了，于是买了域名（¥68/年）、一台 2 核 4G 的服务器（¥68/月）、接了 DeepSeek 的 API、写了支付回调。第一天部署完，网站能打开，我高兴得跟什么似的。第二天开始，麻烦就来了。 I demoed it to three friends and each of them said "you could sell this right now." I believed them, so I bought a domain (¥68/year), a 2-core 4GB server (¥68/month), wired up the DeepSeek API, and wrote the payment callback. On the first day the site went live and I was thrilled. Starting the next day, the trouble arrived.

后来我把这句话想明白了：Demo 的验收标准是「5 个功能能演一遍」，上线的验收标准是「在真实用户、真实数据、真实故障下，连续 30 天不出事」。这两件事需要的代码量并不一样 —— 我这次量了一下，改造成本大约是 Demo 开发成本的三倍。I later boiled it down to this: a demo is accepted when "the five features can be demoed"; a production release is accepted when "nothing breaks for 30 days under real users, real data, and real failures."Those two bars need very different amounts of code — I measured it this time, and the retrofit cost came to roughly three times the cost of building the demo in the first place.

「能跑」和「能上线」之间的 6 个真实差距Six Real Gaps Between "It Runs" and "It's Live"

AI 写代码的时候，会默认一堆前提：单机运行、开发环境、只有你一个人在用、网络不会抖、失败了可以重来。上线这件事，恰好把这五个前提全部推翻。我踩到的 6 个差距，按出现的先后顺序是这样的。 When AI writes code it silently assumes a pile of things: a single machine, a development environment, only you using it, a network that never hiccups, and failures you can retry away. Going live invalidates all five assumptions. Here are the six gaps I hit, in the order I hit them.

  • 密钥硬编码在代码里。AI 生成的 config.js 里有这么一行：const API_KEY = "sk-xxxxxxxx"。Demo 阶段无所谓，反正只有你看得到。Secrets hardcoded in the source. The AI-generated config.js contained a line like const API_KEY = "sk-xxxxxxxx". Harmless during a demo, since you are the only person who sees it.
  • 错误处理等于一句弹窗。所有 catch 块里都是 alert('出错了')。用户看到一句废话，而你知道得比他还少。Error handling is one toast. Every catch block contained alert('something went wrong'). The user gets a useless message and you know even less than they do.
  • 没有日志，没有监控。代码跑完就消失了。用户说"我昨天上午提交失败过"，你想查也查不到，因为那件事没有被记录下来。No logs, no monitoring. Code ran and vanished. A user says "my upload failed yesterday morning" and there is nothing to look up, because the event was never recorded.
  • 成本没有上限。模型调用既不限流也没有预算闸门。一个写错的小脚本循环了 800 次，账单就成了一条往上爬的直线。No ceiling on cost. Model calls were neither rate-limited nor budget-capped. A small buggy script looped 800 times and the bill became a straight line climbing up.
  • 出了问题不能回滚。每次上线都是直接覆盖线上代码。发现 bug 只能改代码重新部署，一轮 20 分钟；半夜出 bug，那 20 分钟会显得很长。No way to roll back. Every deploy overwrote the live code in place. The only fix was to edit and redeploy — a 20-minute cycle that feels much longer at 3 a.m.
  • 没有测试。改一行，不知道会不会弄坏别的功能。唯一的测试方式是"我自己再点一遍"，而我点的是我熟悉的路径。No tests. Change one line and you cannot tell what else you broke. The only test is "I'll click through it again myself" — and I only click the paths I know.
这 6 条不是我的个人偏好These Six Are Not Personal Preferences

它们是 AI 生成代码的默认假设：单机、开发环境、只有一个用户、网络稳定、失败可重试。你不需要重新发明生产化工程，你只需要意识到这些假设存在，然后一条条把它们改掉。They are the default assumptions baked into AI-generated code: single machine, dev environment, one user, stable network, failures are retryable. You do not need to reinvent production engineering — you just need to notice those assumptions exist and remove them one by one.

第一课：密钥不能住在代码里Lesson One: Secrets Must Not Live in Your Code

最简单的一条原则：凡是叫 key、token、secret、password 的东西，都不应该出现在源码里，更不应该出现在 Git 历史里。本地开发时用 .env 文件，部署时用云平台的环境变量面板，两边代码只写读取逻辑。 The simplest rule of all: anything named key, token, secret, or password does not belong in source code, and even less so in Git history. Use a .env file locally, the platform's environment-variable panel in production, and let the code only read them. 

# .env —— 只存在于你自己的机器上，绝不提交
DEEPSEEK_API_KEY=sk-xxxxxxxxxxxxxxxxxxxxxx
APP_SESSION_SECRET=3f9a1c2e7b4d8a65

# .gitignore 里一定要有这几行
.env
.env.*
!.env.example

# 本地运行时把 .env 读进环境变量
node --env-file=.env server.js

# 代码里只读环境变量，永远不写死
const apiKey = process.env.DEEPSEEK_API_KEY;

仓库里保留一个 .env.example，里面只写变量名不写值，这样别人 clone 下来也知道要配什么。至于部署：服务器上用 systemd 或 Docker 的 env_file，托管平台就用它们的环境变量面板。别做的事只有一件：把密钥写进 Dockerfile、写进 docker-compose.yml 的 environment、或者贴到聊天群里。 Keep an .env.example in the repo with the variable names but no values, so anyone who clones it knows what to configure. For deployment, use systemd's or Docker's env_file locally and the platform's environment-variable panel on managed hosts. There is exactly one thing not to do: never put a key in the Dockerfile, in docker-compose.yml's environment block, or in a chat group.

上线前该有的样子What production should look like

密钥放在平台的环境变量面板里；代码里只出现 process.env.DEEPSEEK_API_KEY；本地用 .env 并写进 .gitignore；仓库只留 .env.example；给 key 设置单日消费上限，异常用量自动告警。The key lives in the platform's environment-variable panel; the code only ever mentions process.env.DEEPSEEK_API_KEY; locally you use a .env that is in .gitignore; the repo keeps only .env.example; and the key has a daily spend cap with an alert on abnormal usage.

AI 常给的样子What AI usually gives you

密钥写在 src/config.js 里，跟着代码一起提交；或者写进 docker-compose.yml 的 environment，跟着镜像一起构建。"本地能跑就行"在 Demo 阶段是真话，在上线阶段是定时炸弹。The key sits in src/config.js and is committed with the code; or it is baked into docker-compose.yml's environment and ships inside the image. "It runs locally" is true during a demo and a time bomb at launch.

真实事故：密钥泄漏Real Incident: Key Leak

2026 年 4 月，我在一个开源项目模板里用了自己的 DeepSeek key，直接写死在前端 config 文件里。仓库是私有的，我一直觉得没事。问题出在：一个朋友 fork 了这个模板并发到了社区。当天晚上 11 点我收到平台邮件，说这个 key 的调用量异常，已自动冻结。我登录账单一看——8 小时里被刷了 190 万 token，¥1,340。这是我为「密钥不进代码」这件事交的第一笔学费。In April 2026 I used my own DeepSeek key inside an open-source project template, hardcoded in a frontend config file. The repo was private and I assumed that was enough. What actually happened: a friend forked the template and shared it with a community. At 11 p.m. I got an email from the provider saying usage on that key was abnormal and the key had been auto-frozen. The billing page told the rest — 1.9 million tokens burned in eight hours, ¥1,340. That was the first tuition I paid for the rule "no secrets in code".

钱不算多，要命的是那天正好有一笔收入要提现，余额被冻结导致提现失败，我多等了 3 个工作日。事后我做了 5 件事：立刻 revoke 掉旧 key；换新 key；在平台把单日消费上限设成 ¥50；加了一条"当日调用量超过 3 倍均值就报警"的规则；最后把 git log -S "sk-" 写进上线检查清单——这条能查出历史里有没有漏网的密钥，包括那些你以为已经删干净的。The money was not the worst part. The worst part was that I had a payout scheduled that night; the frozen balance blocked it and I lost three business days. Afterwards I did five things: revoked the old key immediately; issued a new one; set a ¥50 daily spend cap on the provider; added an alert for "daily calls above 3× the average"; and finally put git log -S "sk-" into my launch checklist, because that command finds keys you thought you already deleted.

第二课：把每一个外部输入都当成陌生人Lesson Two: Treat Every External Input as a Stranger

Demo 阶段输入都来自你自己：你的测试合同、你敲的关键词。上线之后，输入来自陌生人——上传的文件、表单里填的字段、URL 上的参数、甚至伪造的请求头。这些东西都要当作"敌人"来对待，而不是"数据"。 During the demo, every input came from you: your own test contract, your own keywords. Once you are live, inputs come from strangers — uploaded files, form fields, URL parameters, even forged headers. All of them should be treated as hostile data rather than as data.

  • 输入校验要在入口做。校验类型、长度、范围、格式。文件上传要限制扩展名和大小（我只收 pdf/docx 且不超过 10MB）。不要相信前端的校验，因为前端可以被绕过。Validate at the boundary. Check type, length, range, and format. For uploads, restrict the extension and the size (I only accept pdf/docx up to 10MB). Never trust validation on the frontend, because the frontend can be bypassed.
  • SQL 注入。AI 特别喜欢写字符串拼接的 SQL：db.query("SELECT * FROM users WHERE email = '" + email + "'")。正确写法是参数化查询：db.query("SELECT * FROM users WHERE email = ?", [email])。ORM 也一样，用它的查询构造器，别自己拼。SQL injection. AI loves string-concatenated SQL: db.query("SELECT * FROM users WHERE email = '" + email + "'"). Use parameterised queries instead: db.query("SELECT * FROM users WHERE email = ?", [email]). The same goes for ORMs — use the query builder, never raw concatenation.
  • 命令注入。不要把用户输入拼进 shell。AI 常写 exec('ffmpeg -i ' + filePath)，一个带空格或分号的文件名就完蛋。正确做法是参数数组：execFile('ffmpeg', ['-i', filePath])。Command injection. Never concatenate user input into a shell command. AI likes exec('ffmpeg -i ' + filePath), and one filename with a space or a semicolon is all it takes. Use an argument array instead: execFile('ffmpeg', ['-i', filePath]).
  • XSS。用户内容要先转义再渲染。不要用 innerHTML 直接塞用户字符串，用 textContent，或者用框架默认的转义机制。合同内容一定会包含 < 和 & 这类字符，不转义一定会出事。XSS. Escape user content before rendering it. Don't stuff user strings into innerHTML; use textContent or let your framework's default escaping handle it. Contract text is guaranteed to contain characters like < and &, so skipping escaping is a matter of when, not if.
  • 依赖漏洞。AI 很爱用"看起来很流行"的包，其中一部分已经三年没更新了。每次上线前跑一次 npm audit，把 high 和 critical 级别先修掉；暂时修不掉的，至少确认你的代码没有调用那个有漏洞的功能。Dependency vulnerabilities. AI loves packages that "look popular", and some of them have not been updated in three years. Run npm audit before every release and fix the high and critical ones; if something cannot be fixed yet, at least confirm your code never calls the vulnerable path.
5 分钟自查法A 5-Minute Self-Check

把 AI 生成的代码通读一遍，凡是出现 exec、拼接的 SQL、innerHTML 的地方，全部标出来。这三样加上硬编码密钥，基本覆盖了 90% 的线上安全问题。我第一次做这件事的时候，标出了 7 处，全部是我在 Demo 阶段根本不会注意到的地方。Read through the AI-generated code once and mark every occurrence of exec, concatenated SQL, and innerHTML. Those three, plus hardcoded secrets, cover about 90% of real production security incidents. The first time I did this I marked seven spots — none of which I would ever have noticed while building the demo.

第三课：先量，再优化Lesson Three: Measure First, Then Optimize

性能这件事最怕凭感觉。我给自己定的规矩是：先给每个关键接口加一行耗时日志，让真实用户跑一遍，把数字记在纸上，再决定改什么。下面是我这次实际改出来的效果。 Performance work goes wrong when you go by feel. My rule was: add one timing log to every critical endpoint, let real users exercise it, write the numbers down, and only then decide what to change. Here is what actually moved after the fixes.

  • 首屏 4.2s → 1.3s。打包进首屏的 JS 有 1.8MB，其中一半是 AI 塞进去但根本没用到的图标库和日期库。删掉无用依赖、路由懒加载、图片转 WebP 之后，gzip 后只剩 620KB。First paint 4.2s → 1.3s. The initial JS bundle was 1.8MB, and half of it was icon and date libraries the AI pulled in that nothing actually used. After dropping unused dependencies, lazy-loading routes, and converting images to WebP, the gzipped bundle was 620KB.
  • 列表接口 P95 2.6s → 180ms。典型的 N+1 查询：页面要显示 20 份合同，每份合同再单独查一次签署人，一页打了 47 次数据库。改成一次 JOIN 之后变成 3 次查询。List endpoint P95 2.6s → 180ms. A textbook N+1: the page shows 20 contracts and looks up one signatory per contract, so a single page view fired 47 database queries. One JOIN brought it down to 3.
  • 最慢的 SQL 3.1s → 12ms。contracts 表没给 status + created_at 建索引。EXPLAIN 出来是全表扫描，加了个复合索引之后变成走索引。Slowest SQL 3.1s → 12ms. The contracts table had no index on status + created_at. EXPLAIN showed a full table scan; a composite index turned it into an index scan.
  • 偶发 502 消失了。AI 生成的代码每次请求都新建数据库连接，100 个并发直接把连接数打满。改成连接池，最大 10 个连接之后，502 从"每天十几次"变成 0。The random 502s vanished. The AI-generated code opened a new database connection per request, so 100 concurrent users exhausted the connection limit. With a pool capped at 10 connections, the 502s went from "a dozen a day" to zero.

该做的顺序The right order

先给接口加耗时日志 → 找到最慢的 3 条 SQL → 用 EXPLAIN 看执行计划 → 加索引、消灭 N+1 → 再删无用前端依赖 → 最后才考虑缓存和 CDN。每一步都有数字支撑。Add timing logs → find the three slowest SQL statements → read their EXPLAIN plans → add indexes and kill the N+1 → then drop unused frontend dependencies → only afterwards consider caching and a CDN. Every step is backed by a number.

常见的误区The common mistake

一上来就加 Redis、换更大的服务器、把接口挂 CDN。这些都是在还没定位问题之前的猜测，很可能花三天时间还没效果——因为慢的根本不是数据库，而是那段一次查 47 次的循环。Adding Redis, buying a bigger server, putting the API behind a CDN. All of these are guesses made before you know what is slow, and they can burn three days with no result, because the bottleneck was never the database — it was a loop that queried 47 times.

第四课：模型调用要算账Lesson Four: Budget Your Model Calls

AI 应用和普通 SaaS 最大的区别是：你的成本和用户使用量成正比，而且是变动成本。Demo 阶段 10 个用户一天几分钱，1 万用户一天可能几百块。所以这件事必须在写第一行代码之前算清楚，而不是等账单来了再 surprise。 The biggest difference between an AI app and an ordinary SaaS is that your cost scales with usage and is a variable cost. Ten users cost pennies a day during the demo; ten thousand users can cost hundreds a day. So you compute this before writing the first line of code, not when the invoice arrives.

我的估算法就三步：一是数调用频次（一个用户一天用几次，保守一点按 8 次算）；二是估 token 量（我这次平均输入 1500 token、输出 400 token，包含那段固定的系统提示词）；三是乘单价，然后再留 30% 冗余。公式很简单：月成本 ≈ 日活 × 人均调用次数 × 30 ×（平均输入 token × 输入单价 + 平均输出 token × 输出单价）。 My estimation is three steps: count the call frequency (how many times one person uses the product per day — I used a conservative 8); estimate the tokens (for me, 1,500 input and 400 output tokens on average, including the fixed system prompt); multiply by the price, then add a 30% buffer. The formula is simple: monthly cost ≈ DAU × calls per user × 30 × (avg input tokens × input price + avg output tokens × output price).

// 每个用户：每分钟最多 5 次、每天最多 200 次模型调用
const RATE_LIMIT = { perMinute: 5, perDay: 200 };

export async function callModel(userId, prompt) {
  const dayKey = `llm:${userId}:${today()}`;

  // 1) 用户级日配额
  const used = await redis.incr(dayKey);
  await redis.expire(dayKey, 86400);
  if (used > RATE_LIMIT.perDay) {
    throw new Error('今日额度已用完，请明天再试');
  }

  // 2) 全局预算闸门：当日花超了就不再调用模型
  const spent = await redis.get('llm:budget:today');
  if (Number(spent) > DAILY_BUDGET_YUAN) {
    throw new Error('今日预算已用尽，已临时停用 AI 功能');
  }

  // 3) 真正调用
  return openai.chat.completions.create({
    model: 'deepseek-chat',
    messages: [{ role: 'user', content: prompt }],
  });
}
缓存是最容易被忽略的省钱手段Caching Is the Cheapest Saving You Will Miss

我的系统提示词每次调用都一样，大约 1200 token。开了 prompt caching 之后，这部分单价从 ¥2/百万 降到 ¥0.2/百万。一个月下来，命中缓存的那 1.5 亿 token 省了约 ¥270 —— 折合每个活跃用户 0.27 元。别小看这个数字：缓存基本上就是改一行配置的事，比限流还简单。My system prompt is identical on every call — about 1,200 tokens. With prompt caching enabled, that part drops from ¥2 to ¥0.2 per million tokens. Over a month, the 150 million cached tokens saved roughly ¥270, which is ¥0.27 per active user. Don't underestimate it: caching is essentially a one-line configuration change, simpler than rate limiting.

第五课：出事的时候，你必须看得见Lesson Five: When It Breaks, You Must Be Able to See It

上线前我给自己设的最后一道心理防线是：出问题时，你得能在 5 分钟内回答"哪个用户在什么时候遇到了什么错误"。做不到这一点，前面所有的努力都会在第一次线上故障里被冲垮——因为你连问题出在哪都不知道。 The last line of defence I drew before going live was this: when something breaks, you must be able to answer "which user, at what time, hit what error" within five minutes. If you can't, everything else you built gets wiped out by the first real incident, because you won't even know where to look.

最少要有的 5 条日志The 5 Logs You Cannot Skip

  • 每个请求的入口日志：用户 ID、路径、耗时、结果状态。Entry log for every request: user ID, path, duration, outcome status.
  • 每次模型调用的日志：模型名、输入输出 token 数、耗时、有没有重试、是否命中缓存。Log for every model call: model name, input/output token counts, duration, retry count, cache hit.
  • 每笔写操作（创建 / 修改 / 删除）：谁做的、改了哪个对象、改前改后的关键字段。Every write operation (create / update / delete): who did it, which object, the key fields before and after.
  • 每一次外部依赖失败：超时、5xx、重试了几次、最后放弃了没有。Every external dependency failure: timeout, 5xx, retry count, and whether it ultimately gave up.
  • 每一条异常：完整堆栈 + 用户 ID + request id，三者必须能串成一条线。Every exception: the full stack trace plus user ID plus request id, and all three must be joinable into a single thread.

1 个错误上报 + 2 个告警1 Error Reporter + 2 Alerts

  • 错误上报：Sentry 的免费版就够了。它能自动关联到具体 commit，异常一多就发邮件通知，比你自己翻日志快十倍。Error reporting: the free Sentry tier is enough. It links errors to the exact commit and emails you when the volume spikes — ten times faster than reading logs by hand.
  • 告警一（可用性）：5 分钟内错误率超过 2%，或者连续 10 个请求失败，立刻通知我。Alert 1 (availability): error rate above 2% over 5 minutes, or 10 consecutive failed requests — notify me immediately.
  • 告警二（成本）：当日模型调用费用达到日预算的 50% 和 100% 时各通知一次。Alert 2 (cost): notify once when the day's model spend reaches 50% of the daily budget and again at 100%.
// 结构化日志：一行一个 JSON，方便 grep，也方便以后接日志平台
function log(event, fields = {}) {
  console.log(JSON.stringify({
    ts: new Date().toISOString(),
    event,          // 事件名，例如 'llm.call'
    requestId,      // 贯穿一次请求的追踪 ID
    userId: fields.userId,
    ...fields,
  }));
}

最后一条经验：request id 要从网关一路传到日志和错误上报里。没有它，用户截图说"刚才失败了"，你只能靠时间范围去猜，猜错的概率很高。 One last piece of advice: the request id must travel from the gateway all the way into your logs and error reports. Without it, when a user sends a screenshot saying "it just failed", you can only guess by time window — and you will guess wrong more often than you would like.

我这次是怎么一步步改的How I Refactored It, Step by Step

整个改造花了 3 周，顺序比内容更重要。下面是我实际走过的六步，你可以按这个顺序照着做，也可以按自己的项目裁剪。 The whole retrofit took three weeks, and the order mattered more than the content. These are the six steps I actually took — you can follow them as-is or adapt them to your project.

第 1 步：先补日志和错误上报（0.5 天）Step 1: Add logs and error reporting first (half a day)

在改任何功能之前，先让系统"能说话"。没有日志，后面所有的优化都是盲改——你连改完有没有变好都不知道。这一步做完，我只花了一个下午。Before touching a single feature, make the system able to talk. Without logs, every later optimisation is blind — you would not know whether your change helped. This took me one afternoon.

第 2 步：把密钥搬出代码（1 天）Step 2: Move every secret out of the code (one day)

换环境变量、轮换所有已经在 Git 历史里出现过的 key、把 .env 写进 .gitignore、在 CI 里加一条 git log -S "sk-" 的检查。顺手把 DeepSeek 的单日消费上限设成 ¥50。Switch to environment variables, rotate every key that ever appeared in Git history, add .env to .gitignore, and put a git log -S "sk-" check in CI. While I was there I also set a ¥50 daily cap on the model provider.

第 3 步：给每个外部调用加超时和重试（1 天）Step 3: Add timeouts and retries to every external call (one day)

模型调用、数据库、对象存储，全部加超时；只有幂等的调用才重试，重试次数上限 2 次，并且重试之间要等一个递增的间隔。这一步顺手解决了一个必现的 bug：模型偶尔会卡住 30 秒，把整个请求线程占死。Model calls, the database, object storage — all of them got a timeout. Only idempotent calls are retried, at most twice, with a growing delay between attempts. This also killed a reproducible bug: the model would occasionally hang for 30 seconds and pin the request thread.

第 4 步：加索引、消灭 N+1（2 天）Step 4: Add indexes and kill the N+1 (two days)

先用 EXPLAIN 找出最慢的 3 条 SQL，再动手改。改完之后列表接口 P95 从 2.6s 降到 180ms，首屏 JS 从 1.8MB 降到 620KB。这一步是用户感知最强的一次优化。Use EXPLAIN to find the three slowest SQL statements first, then change the code. Afterwards the list endpoint's P95 went from 2.6s to 180ms and the initial JS from 1.8MB to 620KB. This was the optimisation users noticed most.

第 5 步：加限流、缓存和预算闸门（2 天）Step 5: Add rate limiting, caching and a budget gate (two days)

每个用户每分钟 5 次、每天 200 次；固定 prompt 开缓存；当日预算超过 80% 时自动把非关键功能降级到轻量模型。做完这一步，我那个写错的小脚本再也刷不动账单了。Five calls per minute and 200 per day per user; caching for the fixed prompt; automatic downgrade to a lightweight model once 80% of the daily budget is gone. After this, my buggy script could no longer make the bill move.

第 6 步：补 8 个端到端测试 + 一键回滚（4 天）Step 6: Add 8 end-to-end tests and one-command rollback (four days)

测试覆盖注册、上传、支付、模型调用、失败重试这 5 条主路径；顺手写了 deploy.sh --rollback v12 这个脚本。这一步最花时间，但也是让我后来敢睡觉的一步。The tests cover the five main paths: signup, upload, payment, model calls, and failed-call retries. I also wrote the deploy.sh --rollback v12 script along the way. This was the most time-consuming step and the one that finally let me sleep at night.

顺序上的教训A Lesson About Ordering

第 1 步（补日志）我原本想放到最后，结果改到一半又回来补了一遍，白花了一天半。凡是要靠"观察"才能做好的事，都应该放在最前面——因为观察需要时间，你需要留出时间去观察。I originally planned to do step 1 (adding logs) last, then came back halfway through and did it anyway, wasting a day and a half. Anything that depends on observation belongs at the front, because observation takes time and you need to leave time for it.

上线前的 12 项检查The 12-Item Pre-Launch Checklist

这是我实际用的清单，每次上线前逐条打勾，用不了 5 分钟。前 5 条是安全，后 4 条是可观测性，最后 3 条是保命的。 This is the checklist I actually use. I tick it off before every release; it takes less than five minutes. The first five are security, the next four are observability, and the last three are the ones that keep you in business.

  1. ☐ 仓库里搜不到任何密钥：git grep -n "sk-\|api_key\|secret" 没有结果，git log -S "sk-" 也查不到历史泄漏。☐ No secrets in the repo: git grep -n "sk-\|api_key\|secret" returns nothing, and git log -S "sk-" finds no leak in history.
  2. ☐ 所有密钥都来自环境变量，代码里没有硬编码的 key，也没有 .env 被提交。☐ Every secret comes from an environment variable, no key is hardcoded, and no .env was committed.
  3. ☐ 每个对外接口都做了输入校验（类型、长度、范围、格式），文件上传限制了类型和大小。☐ Every public endpoint validates its input (type, length, range, format), and file uploads are restricted by type and size.
  4. ☐ 没有把用户输入拼进 SQL、shell 命令或 HTML。☐ No user input is concatenated into SQL, shell commands, or HTML.
  5. ☐ npm audit 没有 high / critical 级别的漏洞。☐ npm audit reports no high or critical vulnerabilities.
  6. ☐ 每个外部调用都有超时，重试只加在幂等操作上，重试次数不超过 2 次。☐ Every external call has a timeout, retries are only used on idempotent operations, and never more than twice.
  7. ☐ 关键路径至少有 1 条日志，带 request id，能和错误上报对上。☐ Every critical path logs at least once, carries a request id, and can be joined with the error reports.
  8. ☐ 错误上报已经接上，而且我真的触发过一次测试告警确认它能响。☐ Error reporting is connected, and I have triggered a test alert to confirm it actually fires.
  9. ☐ 两个告警都生效了：错误率告警 + 当日费用告警。☐ Both alerts work: the error-rate alert and the daily-spend alert.
  10. ☐ 模型调用有用户级限流和当日预算上限，脚本批量调用会被挡下来。☐ Model calls have per-user rate limits and a daily budget cap, so scripted bursts get blocked.
  11. ☐ 数据库有备份，并且我演练过一次真的从备份恢复（不是"备份存在"，是恢复过）。☐ The database is backed up, and I have actually restored from a backup once — not "a backup exists", but a real restore.
  12. ☐ 上一个版本的代码和配置还在，能一键回滚，而且我知道回滚要花多长时间。☐ The previous version's code and config are still around, can be rolled back with one command, and I know how long that takes.

如果第 11、12 条没过，就先别上线。这两条是保命的，其余 10 条是让你少受点苦。 If items 11 and 12 are not green, do not launch. Those two keep you in business; the other ten just save you from pain.

回滚与灰度：别把鸡蛋放在一个篮子里Rollback and Gradual Release: Don't Keep All Eggs in One Basket

上线不是"部署一次"，而是"部署一个退得回来的版本"。我以前每次上线都直接覆盖线上代码，出了 bug 只能改代码重新部署，一轮 20 分钟；半夜出 bug，那 20 分钟会显得格外长。 Launching is not "deploying once", it is "deploying a version you can go back to". I used to overwrite the live code on every release, which meant a bug could only be fixed by editing and redeploying — a 20-minute cycle that feels much longer in the middle of the night.

现在我的做法有三条：My current setup rests on three decisions:

  • 每个版本都能一键回滚。每次上线打一个版本号，旧的构建产物至少保留 7 天，回滚就是一条命令：deploy.sh --rollback v12。Every version rolls back with one command. Each release gets a version number, the old build artefacts are kept for at least 7 days, and rolling back is deploy.sh --rollback v12.
  • 配置和代码分开。改配置（换个模型、调个限额、改一句提示词）不需要重新构建，5 秒生效，出问题改回去也是 5 秒。很多"事故"其实只需要改一行配置。Config is separated from code. Changing configuration (a different model, a different limit, one line of prompt) needs no rebuild: it takes effect in 5 seconds, and reverting it also takes 5 seconds. Plenty of "incidents" are really a one-line config change.
  • 数据库变更向前兼容。先加新字段（不动旧字段），应用同时兼容新旧两种结构，下一次上线再删旧字段。这样回滚应用不会因为表结构对不上而失败。Schema changes are forward-compatible. Add the new column first without touching the old one, make the app handle both shapes, and drop the old column in a later release. That way rolling the app back never fails because the table shape moved on.
「回滚方案必须在出故障之前就演练过。没演练过的回滚方案，等于没有回滚方案。」 "A rollback plan you have not rehearsed is not a rollback plan."

再说灰度。我的用户量不大，所以我的"灰度"是按比例放流量： Now for gradual release. My audience is small, so my "gradual release" is simply routing a share of traffic:

  • 新版本先给 10% 的用户用，观察 24 小时 → 放到 50%，再观察 24 小时 → 全量。Ship the new version to 10% of users and watch for 24 hours → move to 50% and watch 24 hours more → then go to 100%.
  • 观察四个指标：错误率、P95 延迟、当日费用、用户投诉数。Watch four metrics: error rate, P95 latency, daily spend, and the number of user complaints.
  • 任何一个指标比基线差 20% 以上，立刻把比例调回去，不用整体回滚。If any metric is more than 20% worse than baseline, dial the percentage back immediately — no full rollback needed.

对独立开发者来说，灰度还有一个更省事的版本：用 feature flag（一个配置项开关）把新功能关掉。新功能出问题，不用回滚整个版本，关掉开关就行。这比任何架构都简单，而且几乎不需要额外成本。 For a solo developer there is an even cheaper form of gradual release: a feature flag — a single configuration switch. If the new feature misbehaves, you turn the switch off instead of rolling back the whole release. It is simpler than any architecture and costs almost nothing.

这一趟花了多久，下次我会怎么做How Long This Took and What I'd Do Differently

从"Demo 能跑"到"敢接真实用户"，这次一共花了 5 周：Demo 开发 5 天，生产化改造 3 周，灰度加观察 1 周。踩了 7 个坑——密钥泄漏（上面那个）、支付回调重复通知导致用户被扣了两次钱、模型超时没有重试、列表页 N+1、没做限流被自己写的小脚本刷掉 ¥380、移动端首屏 8 秒、数据库连接没池化偶尔 502。平均每个坑花掉我一天。 From "the demo runs" to "I dare take real users", the whole thing took five weeks: five days to build the demo, three weeks of production hardening, one week of gradual release and observation. I hit seven real problems — the key leak described above, a payment webhook that notified twice and double-charged a user, no retry on model timeouts, the N+1 on the list page, no rate limiting so my own buggy script burned ¥380, an 8-second mobile first paint, and occasional 502s from an unpooled database connection. On average, each one cost me a day.

如果重来一次，这四件事我会从第一天就做：If I did it again, these four things would happen on day one:

  1. 日志和错误上报从第一天就写，别等。Write the logs and error reporting on day one. Don't wait.
  2. 密钥从第一行代码起就走环境变量，不存在"等上线再改"这回事。Secrets live in environment variables from the very first line. There is no such thing as "I'll fix it before launch".
  3. 模型调用第一天就接限流和预算闸门，别用"回头再加"安慰自己。Rate limits and a budget gate go in on day one. Don't comfort yourself with "I'll add it later".
  4. 给每个外部依赖写一份"如果它挂了会怎样"的问题清单，逐条回答。答不上来的那一条，就是你下次会半夜被叫醒的那一条。For every external dependency, write down the question "what happens if this is down?" and answer each one. The one you cannot answer is the one that will wake you at 2 a.m.
结论The Takeaway

AI 写代码的速度没有变慢，是"以为做完了"的标准太宽松。把"能跑"改成"能扛住真实世界"，这件事 AI 帮不了你——但这份清单可以。AI did not get slower at writing code. My definition of "finished" was simply too loose. Changing "it runs" into "it survives the real world" is not something AI can do for you — but this checklist can.
